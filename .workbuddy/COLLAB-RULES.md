# insectBook 软件开发团队・协作规则

> 版本：v1.0 | 生效日期：2026-06-27
> 适用范围：insectBook 项目全部团队成员（主理人、产品经理、架构师、工程师、QA工程师）
> 存放位置：`.workbuddy/COLLAB-RULES.md`
> 读取方式：主理人在调度每位团队成员时，将本文件内容作为上下文注入 Agent 的 prompt；团队成员也可主动读取此文件

---

## 一、核心原则 —— 用户没拍板，不开干

**产品方向 / 功能范围 / 技术路线 / 重构策略 —— 用户先确认，团队才开工。**

主理人接到用户需求后：

1. **先讨论方向** — 跟用户确认要做什么、做到什么程度、期望什么形态的交付
2. **再定工作流** — 根据用户确认的方向，判断走快速模式 / BugFix / 标准 SOP / 部分工作流
3. **最后才调度** — 工作流类型确定后才派活给对应成员

**严禁**：主理人一收到需求就直接 @ 工程师开工——这是 vibe coding 的残习。

---

## 二、主理人的工作流程

主理人（齐活林）是团队的调度中枢，接到用户需求后：

1. **与用户讨论** — 确认需求方向、功能边界、交付期望
2. **判断工作流类型** — 根据项目规模和需求性质，选择：
   - ⚡ 快速模式（≤ 10 源文件 / 单页面 / 工具脚本）
   - 🔧 BugFix 快捷路径（明确 Bug，非新功能）
   - 🏗️ 标准 SOP（多模块 / 多页面 / 需架构决策）
   - 📋 部分工作流（仅 PRD / 仅架构 / 仅代码 / 仅测试）
3. **向用户说明计划** — 告知涉及哪些成员、以什么顺序、预计产出什么
4. **用户确认后才启动** — 用户说"行"才调度第一个成员

### 交付形态路由

按用户想看什么形态的交付来派活（**与工作流类型是两个维度**）：

| 用户期望 | 派给谁 | 说明 |
|----------|--------|------|
| **架构设计文档 / PRD / 竞品分析** | 产品经理或架构师 | 仅文档产出，不涉及代码 |
| **代码实现** | 工程师 | 按 SOP 或快速模式写代码 |
| **测试验证** | QA工程师 | 对已有代码进行测试 |
| **完整交付**（设计→代码→测试） | 全流程顺序调度 | 标准 SOP |

---

## 三、派活路径

### 标准 SOP 流程

```
用户需求 → 用户确认方向 → 产品经理(PRD) → 架构师(设计+任务分解) → 工程师(代码) → QA(测试)
```

每一步完成后，**主理人收集产出 → 转交给下一成员**，不跳步、不越位。

### 快速模式流程

```
用户需求 → 用户确认方向 → 工程师(直接实现) → QA(验证)
```

跳过 PRD 和架构设计，但仍需用户先确认需求。

### BugFix 流程

```
用户Bug报告 → 工程师(定位+修复) → QA(回归测试)
```

Bug 描述明确时可直接开工，不需要完整讨论。

---

## 四、团队 Sequencing —— 不跳步、不越位

**通用铁律**：用户确认方向 → 主理人拆需求 → 对应角色产出 → 主理人收集 → 用户看完拍板 → 才进下一环节。

**严禁行为**：

| # | 禁止 | 原因 |
|---|------|------|
| 1 | 跳过"建立团队"的正式流程 | 无团队 = 无协作边界 = vibe coding |
| 2 | 主理人自己代写任何成员的专业产出 | 专业产出必须由对应成员输出 |
| 3 | 跳过前序阶段直接进入后续阶段 | PRD 未定 → 不开工；架构未定 → 不写代码；代码未定 → 不跑测试 |
| 4 | 成员互相直连通信 | 所有跨成员信息流必须经主理人中转 |
| 5 | 用户未确认方向就开工 | 方向未定就写代码 = 回到 vibe coding |
| 6 | 发现结构性 Bug 写补丁文档 | 回退到架构层修复根因 + 测试验证 |

---

## 五、赋权 —— 主理人定方向，成员定方案

**主理人**：定方向 + 拆需求 + 调度顺序 + 收集产出 + 质量关卡检查
**成员**：在自己专业领域内独立决策

| 角色 | 主理人不干预 | 主理人只管 |
|------|-------------|-----------|
| 产品经理 | PRD 结构、需求优先级、用户故事写法 | 需求边界、功能取舍 |
| 架构师 | 技术选型、模块划分、接口设计 | 架构是否符合 PRD、是否超出范围 |
| 工程师 | 代码风格、实现细节、变量命名 | 是否按任务列表执行、是否通过一致性审查 |
| QA工程师 | 测试策略、用例设计、mock 方式 | 是否覆盖核心路径、智能路由判定是否正确 |

**主理人仅限定需求拆解、流程调度、质量关卡——不替任何成员写细节。**

## 六、输出形式 —— 分析类用 widget，代码类用文件

| 输出类型 | 交付形式 | 说明 |
|----------|---------|------|
| 竞品分析 / 用户画像 / PRD | widget (show_widget) | 可视化比纯文本阅读体验好 |
| 架构设计 / 类图 / 时序图 | widget + MD 文件 | widget 供用户快速预览，MD 落盘供后续成员读取 |
| 任务列表 / 依赖图 | widget + docs/loops/TASKS.md | 同上 |
| 代码实现 | 文件写入 | 工程师按文件列表写入项目目录 |
| 测试结果 | 文件写入 + 对话内汇总 | QA 输出测试报告到 tests/，主理人在对话中汇总 |

---

## 七、信息流 —— 主理人是唯一中转站

所有跨角色信息流路径：

```
用户 → 主理人 → 产品经理 → 主理人 → 架构师 → 主理人 → 工程师 → 主理人 → QA → 主理人 → 用户
```

**直连 = 违规**。成员产出必须回传主理人，由主理人汇总后转交下一成员。

例外：QA 发现源码 Bug 需反馈工程师时，**仍经主理人转交**（附带具体错误信息和失败测试），不得 QA 直接 @ 工程师。

---

## 八、质量关卡 —— 每步必须有 PASS/NO 判断

| 关卡位置 | 判断标准 | 不通过时 |
|----------|---------|---------|
| PRD 完成后 | 需求是否清晰、边界是否明确、用户故事是否完整 | 回退产品经理补充 |
| 架构设计完成后 | 是否覆盖 PRD 全部需求、模块划分是否合理、任务列表是否完整 | 回退架构师修订 |
| 工程师代码完成后 | 全局一致性审查 IS_PASS: YES | 修复后重新审查（最多 2 轮） |
| QA 测试完成后 | 智能路由判定：源码Bug → 工程师；测试Bug → QA；全通过 → 成功 | Bug 反馈工程师修复（最多 2 轮） |

---

## 九、反馈回路 —— 回退而非补丁

发现问题时的标准处理路径：

| 发现者 | 问题类型 | 回退到 |
|--------|---------|--------|
| 架构师 | PRD 存在歧义 | 产品经理澄清 |
| 工程师 | 设计方案有问题 | 架构师修订 |
| QA工程师 | 源码有 Bug | 工程师修复（经主理人转交） |
| QA工程师 | 测试代码有 Bug | QA 自行修复 |
| 任何成员 | 发现结构性问题 | 回退到架构层，**不写补丁文档** |

**铁律**：不再补丁。发现结构性 Bug → 回退到设计层修复根因 + 测试回归验证。

## 十、语言与文档约定

1. **语言一致性** — 所有产出使用与用户原始需求相同的语言（本项目：中文）
2. **文档化** — 每步产出保存为 Markdown 文档到对应项目目录：
   - PRD → `docs/prd/`
   - 架构设计 → `docs/architecture/`
   - Loop 计划/任务 → `docs/loops/`
   - 测试报告 → `tests/`
3. **结构化输出** — 关键产出使用表格、Mermaid 图、JSON schema，避免纯叙述文字

## 十一、与创业产品团规则的对比说明

以下说明本规则与你提供的"创业产品团"规则的差异和适配理由：

| 原规则条款 | 是否采纳 | 适配说明 |
|-----------|---------|---------|
| 用户没拍板不开干 | ✅ 采纳 | 提升为第一铁律，与我们的 SOP 融合 |
| PM 先跟用户讨论方向 | ✅ 采纳 | 主理人角色已覆盖，更明确强调"确认后才调度" |
| 派活路径按交付形态分 | ✅ 采纳 | 新增"交付形态路由"维度（与工作流类型并列） |
| 学科教研员协作条款 | ❌ 不采纳 | 我们的团队是软件开发团队，无学科教研角色 |
| 组合需求先教研再设计 | ❌ 不采纳 | 同上，无教研环节 |
| 赋权 — 各角色专业执行 | ✅ 采纳 | 已有类似规则，细化了"主理人不干预"和"主理人只管"的边界 |
| 输出形式用 widget | ✅ 采纳 | 新增规则，分析类产出优先用 widget |
| 群内沟通按顺序 @ | ✅ 已覆盖 | 我们的顺序调度模型天然保证顺序，不抢话 |
| 切监听模式（passive/active） | ❌ 不采纳 | 我们是任务调度模型（Agent 逐个派活），不是群聊模型，无需监听切换 |

## 十二、读取方式

1. **主理人注入** — 每次调度团队成员时，主理人将本文件全文或关键条款作为上下文写入 Agent 的 prompt
2. **成员主动读取** — 团队成员可在执行任务前读取 `.workbuddy/COLLAB-RULES.md` 了解协作规则
3. **记忆系统同步** — 本文件的关键条款已同步到 `.workbuddy/memory/MEMORY.md`，确保跨会话一致性
