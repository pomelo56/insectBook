# 架构决策记录 (ADR)

## ADR-001: 选择云开发而非自建后端

**决策**：使用微信云开发（云函数 + 云数据库），不自建 Node/Python 后端。

**理由**：
- insectBook 是微信小程序，云开发与小程序天然集成（免鉴权、免域名配置）
- 用户量预期 < 10万，云开发免费额度足够
- 无需运维服务器、无需域名备案、无需 SSL 配置
- 开发者只需关注业务逻辑，基础设施由微信托管

**代价**：
- 云函数有并发和超时限制（1000并发/60s超时）
- 云数据库查询能力弱（不支持复杂聚合、无事务）
- 数据迁移受限（无自动备份、导出需手动）
- 被绑定在微信生态内（不可迁移到其他平台）

## ADR-002: 豆包视觉API（火山方舟）做昆虫识别

**决策**：使用字节跳动的豆包视觉 API（火山方舟），不自建模型、不用其他 API。

**理由**：
- 豆包视觉 API 支持图片分类/识别，适配昆虫场景
- 火山方舟提供稳定的 API 接口和文档
- 成本可控（按调用次数计费）

**代价**：
- 依赖第三方 API（服务不可用 = 识别功能挂）
- 需要图片转 base64 上传（流量和时间开销）
- 识别准确率受限于模型能力

## ADR-003: Behavior + globalData 做状态管理，不用 MobX/Vuex

**决策**：使用微信小程序的 `Behavior` + `app.globalData` 做状态管理，不引入第三方状态管理库。

**理由**：
- 微信小程序不支持 npm 包的动态引入（需预构建到 miniprogram_npm）
- Behavior 是微信原生机制，无需额外依赖
- insectBook 的跨页状态简单（用户收集列表 + 等级），不需要复杂的状态树
- globalData + onShow 刷新 = 足够应对当前数据流

**代价**：
- Behavior 只能做 mixin（共享方法），不是真正的响应式状态
- 状态变更需手动触发 onShow 刷新，不是自动响应
- 未来如果状态复杂度增长，可能需要引入更好的方案

## ADR-004: 增量重构而非完全重写

**决策**：选择增量重构（Loop Engineering），不完全重写。

**理由**：
- 项目已有真实用户数据（insects + user_insects 集合），完全重写需重新部署和迁移
- 增量重构可以边用边改，不停服
- 每个 Loop 独立分支开发，失败只影响当次 Loop，不影响已合并的部分
- 完全重写风险更大（新代码可能有新 Bug，老数据的兼容性不确定）

**代价**：
- 增量重构需要更多时间和耐心
- 期间新旧代码并存，需要临时兼容方案
- 每次合并需要仔细验证不破坏已有功能

## ADR-005: externalId 替代 name 做 ID 查询

**决策**：所有昆虫查询从 name 改为 externalId。

**理由**：
- name 可变（改名需求）且不唯一（同名昆虫）
- externalId 不可变且唯一（格式: insect-{number}）
- 用 name 查询会导致 INSECT_NAME_MAP 等硬编码映射表，违反 Agentic Engineering 原则

**代价**：
- 需要一次性数据迁移（为所有昆虫记录添加 externalId）
- 需要更新所有引用 name 查询的代码
- 迁移期间需要兼容新旧 ID（过渡期双查）
